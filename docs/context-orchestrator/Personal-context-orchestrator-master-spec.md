# Personal Context Orchestrator — Master Spec

## 0. Purpose of this document

This document is the canonical description of the full target system.
It is not a v0 note, not a feature brief, and not a lightweight prototype outline.
It defines the intended production-grade instrument as a provider-agnostic context infrastructure layer for models and agents.

Its role is to become the source of truth for:
- future architecture documents;
- data model specifications;
- MCP and API contracts;
- read/write/handoff logic;
- implementation sequencing for coding agents;
- boundaries between context control, storage, retrieval, runtime, and base model execution.

---

## 1. Working name

**Provider-Agnostic Personal Context Orchestrator**

Alternative internal names:
- Personal Context OS
- Context Control Layer
- Bounded Context Broker
- Context Infrastructure Layer
- Context Operating Layer for AI

In this document we use:
**Personal Context Orchestrator**

---

## 2. Core thesis

The system is an external context control layer for AI models and agents.

Its job is not to solve the user task instead of the model.
Its job is to decide:
- what context should be remembered;
- what state is active now;
- what context is relevant for the current task;
- what bounded bundle must be delivered to the model;
- what the model may request additionally;
- what should be written back after the interaction;
- how continuity survives across sessions, tasks, workflows, agents, and providers.

### Canonical statement

> The main model must not operate directly on raw history or full storage.
> The main model should operate through bounded context bundles generated by an external context control layer.

---

## 3. Problem the system solves

Modern models and agent stacks remain weak at continuity across:
- sessions;
- tasks;
- workflows;
- roles;
- agents;
- model providers.

Without a dedicated context layer, systems usually degrade into one of the following:
- oversized conversations used as pseudo-memory;
- RAG-only designs that retrieve documents but do not manage continuity;
- vendor-specific memory features tied to one runtime;
- unstructured summaries that lose provenance and active state;
- noisy prompts with poor boundedness;
- weak or missing handoff between agents and sessions.

### Practical consequences

Without a context orchestrator:
- each session restarts close to zero;
- active state is lost;
- open loops disappear;
- long-term and short-term memory are mixed;
- memory becomes noisy and ungoverned;
- context transfer between tools and agents becomes unreliable;
- portability across models becomes weak;
- there is no neutral control point over context decisions.

---

## 4. What this system is not

### 4.1. Not plain RAG
RAG answers the question: what information should be retrieved from knowledge sources?
This system answers broader questions:
- what should be remembered at all;
- what is active state vs archival knowledge;
- what should be shown now;
- what should be carried into the next step;
- what should be passed to another agent;
- what should be compressed, archived, or ignored.

### 4.2. Not chat memory
Conversation history is only one input stream.
The system is not a chat-history wrapper.

### 4.3. Not a vector database
Embeddings may be used as an index, but vector search is not the core architecture.

### 4.4. Not only a runtime feature
The orchestrator must not be trapped inside one framework or one provider.
It should exist as an external layer that can serve multiple runtimes and clients.

### 4.5. Not simply one more LLM on top
The control logic does not have to be a large model.
The strongest architecture is likely hybrid:
- hard rules;
- scoring and ranking logic;
- typed policies;
- selectors;
- optional lightweight semantic classifiers;
- bounded packers;
- governed write gates.

---

## 5. Main function of the instrument

### Canonical function

> Transform accumulated personal, project, workflow, and interaction context into task-shaped bounded context bundles for models and agents.

The system must:
1. receive a user or task signal;
2. identify intent, mode, and relevant scope;
3. select context candidates from memory, state, and related artifacts;
4. remove noise and stale records;
5. package bounded context for the current model invocation;
6. expose tools for controlled context expansion;
7. process post-turn writeback through a governed candidate-to-record flow;
8. preserve continuity for future sessions and handoffs.

---

## 6. First principles

### 6.1. Provider-agnostic
The system must remain usable across multiple model providers and agent environments.
No core design element should assume a single vendor.

### 6.2. Bounded context first
The model must receive bounded bundles, not raw full memory.

### 6.3. Continuity over raw chat history
Continuity should be constructed from typed context objects, state objects, summaries, and handoff artifacts, not from dumping old conversations.

### 6.4. Memory authority outside the model
The model may propose memory candidates, but canonical memory decisions belong to the external context layer.

### 6.5. Layered storage model
Context must be represented through multiple layers, not a single blob.

### 6.6. Separate read, pack, write, and handoff
These are four different responsibilities and must not be collapsed into one generic memory function.

### 6.7. Explainability and auditability
The system must be able to explain:
- why this context was shown;
- why this memory was stored;
- why this state was updated;
- which sources and policies were involved.

### 6.8. Tool-mediated access
The main model should interact with the system through explicit tools/contracts, not opaque hidden access.

## 7. System roles

### 7.1. User
Source of goals, inputs, corrections, signals, preferences, and decisions.

### 7.2. Main model
The model that performs the task:
- answer generation;
- reasoning;
- drafting;
- problem solving;
- tool usage.

### 7.3. Context Orchestrator
The external control layer responsible for:
- selection;
- packing;
- read access governance;
- memory candidate handling;
- state handling;
- handoff creation;
- audit logging.

### 7.4. Storage layer
The persistence layer for events, memory, state, summaries, relations, and bundle artifacts.

### 7.5. Tool gateway
The interface surface between the main model and the orchestrator.
This may be exposed through MCP and/or direct API tools.

### 7.6. Policy and gating engine
The decision layer for:
- storage eligibility;
- scope;
- visibility;
- TTL;
- deduplication;
- conflict handling;
- retention;
- access permissions.

### 7.7. Integration clients
External clients or runtimes such as:
- Codex via MCP;
- ChatGPT via MCP-compatible tool/resource surface;
- agent runtimes;
- local orchestration systems;
- application backends.

## 8. Canonical operating loop

### Step 1 — Input arrives
A user request, workflow event, or agent handoff enters the system.

### Step 2 — Intent and mode detection
The orchestrator determines:
- what kind of task this is;
- whether it is a continuation;
- what operating mode applies;
- how much context budget is justified.

### Step 3 — Scope resolution
The orchestrator decides which domains are relevant and allowed:
- user-global;
- workspace;
- project;
- workflow;
- task;
- session;
- shared agent;
- external artifacts.

### Step 4 — Candidate retrieval
The orchestrator gathers candidate context from multiple layers:
- memory objects;
- active state;
- recent events;
- summaries;
- relations;
- linked resources;
- retrieval indexes.

### Step 5 — Filtering and ranking
The orchestrator filters:
- stale records;
- low-confidence items;
- duplicates;
- irrelevant scope;
- policy-restricted items;
- conflict-heavy candidates.

Then it ranks what remains.

### Step 6 — Bundle packing
A bounded context bundle is created for the current task and target model.

### Step 7 — Main model execution
The model receives:
- system contract;
- user input;
- bounded context bundle;
- available tools;
- rules for when to request additional context or propose memory updates.

### Step 8 — Optional context expansion
If necessary, the model requests more through explicit tools.
The model does not read full memory directly.

### Step 9 — Final answer or action
The model completes the task.

### Step 10 — Post-turn writeback
The system evaluates what should be saved as:
- event;
- memory;
- state;
- summary;
- handoff artifact;
- no-op.

### Step 11 — Audit and continuity update
The system logs decisions and updates continuity surfaces for future steps.

---

## 9. The four core loops

## 9.1. Read loop
Questions answered here:
- what should the model receive now?
- from which scopes?
- with what priority?
- how much is enough?

## 9.2. Pack loop
Questions answered here:
- how should selected context be structured?
- what should be summarized vs kept verbatim?
- what token budget applies?
- what sections must be preserved?

## 9.3. Write loop
Questions answered here:
- what should be written back?
- is this fact, preference, state, decision, open loop, or noise?
- should an existing record be updated or a new one created?

## 9.4. Handoff loop
Questions answered here:
- what should survive into the next session?
- what should be passed to another agent?
- what must be transferred to another provider or model?
- how do we preserve continuity without over-sharing noise?

## 10. Data the system must store

### 10.1. Event log
Raw event trail.

Examples:
- user_message;
- model_response;
- tool_call;
- tool_result;
- state_change;
- handoff_created;
- memory_candidate_submitted;
- memory_written;
- memory_rejected.

Purpose:
- provenance;
- replay;
- audit;
- continuity reconstruction.

### 10.2. Memory objects
Normalized durable memory units.

Core types:
- fact;
- preference;
- constraint;
- goal;
- relationship;
- decision;
- open_loop;
- profile_attribute;
- risk_note;
- artifact_reference.

Minimum fields:
- id;
- type;
- content;
- scope;
- confidence;
- importance;
- freshness;
- source_refs;
- created_at;
- updated_at;
- valid_from;
- valid_to;
- status;
- visibility;
- owner or subject.

### 10.3. State objects
State is not the same as memory.

Examples:
- active_task_state;
- workflow_step;
- pending_question;
- checkpoint;
- waiting_for_input;
- current_mode;
- unresolved_issue;
- active_branch_of_work.

### 10.4. Relations layer
Connections between entities.

Examples:
- user -> project;
- project -> task;
- task -> decision;
- decision -> risk;
- session -> workflow;
- agent -> handoff -> agent;
- artifact -> project.

### 10.5. Summaries and derived views
Derived artifacts such as:
- session summary;
- project summary;
- rolling continuity summary;
- current state brief;
- handoff brief;
- risk digest.

These are derived views, not the sole source of truth.

### 10.6. Context bundles
Generated bounded packages delivered to models or agents.

### 10.7. Retrieval and indexing structures
Indexes used to support candidate discovery:
- semantic index;
- lexical index;
- recency index;
- graph traversal aids;
- scope-oriented lookup tables.

### 10.8. Audit records
Decision traces for why something was selected, packed, written, rejected, or hidden.

## 11. Canonical context classes

The system should distinguish at least these semantic classes:
- stable profile;
- preference;
- temporary preference;
- long-term goal;
- current goal;
- fact;
- hypothesis;
- decision;
- constraint;
- open loop;
- reminder candidate;
- active state;
- workflow state;
- relationship;
- artifact reference;
- risk note;
- instruction-level preference;
- continuity note.

Without explicit type separation, storage collapses into semantic chaos.

## 12. Memory and context scopes

Minimum scope taxonomy:
- global_user;
- workspace;
- project;
- workflow;
- task;
- session;
- agent_local;
- shared_agent;
- organization or team;
- external linked source scope.

Scopes are required for bounded access, routing, isolation, and handoff discipline.

## 13. How the model should receive context

The strongest design is a hybrid read path.

### 13.1. Push path
The system automatically provides a minimal starting context bundle before model execution.

### 13.2. Pull path
The model may request more through explicit tools.

### 13.3. Why not direct memory access
The model must not browse full memory directly because that produces:
- too much noise;
- poor boundedness;
- higher token waste;
- weak policy control;
- unreliable continuity management.

### 13.4. What the model should see
The model should receive:
- the user request;
- a system contract;
- a bounded context bundle;
- available context tools;
- rules for when to request expansion.

---

## 14. How the model should write back

The model should not write canonical records directly.

Correct pattern:
1. the model proposes a candidate;
2. the external gate validates it;
3. policy decides its fate;
4. storage writes the canonical record if approved.

### 14.1. Memory candidate
A candidate is a structured proposal, not an authoritative record.

Minimum fields:
- candidate_type;
- candidate_content;
- suggested_scope;
- confidence;
- why_store;
- source_anchor;
- subject or owner;
- temporal hints if relevant.

### 14.2. State update candidate
State must be handled separately from durable memory.

### 14.3. Gate decisions
The gate decides:
- store or reject;
- update or create;
- memory vs state;
- duplicate or conflict;
- TTL and retention;
- visibility and permissions;
- whether summary refresh is needed;
- whether handoff artifacts should be regenerated.

## 15. Core modules of the full system

### 15.1. Request intake module
Receives user, agent, or workflow signals.

### 15.2. Intent and mode resolver
Classifies the request and selects the operating mode.

### 15.3. Scope resolver
Determines which memory and state scopes are allowed and relevant.

### 15.4. Context selector
Retrieves and ranks candidate context.

### 15.5. Bundle packer
Builds bounded context bundles for a target model or agent.

### 15.6. Main model adapter
Injects the bundle and tool contracts into the chosen model environment.

### 15.7. Tool gateway
Exposes explicit context tools for the model.

### 15.8. Write gate
Processes post-turn candidates through validation, policy, and routing.

### 15.9. Storage manager
Maintains layered persistence and indexes.

### 15.10. Relations engine
Maintains links across entities and improves continuity selection.

### 15.11. Summary engine
Maintains derived continuity artifacts and handoff summaries.

### 15.12. Audit and evaluation layer
Captures decisions and supports diagnostics and quality review.

### 15.13. Policy and governance layer
Controls retention, visibility, scope access, and boundedness rules.

### 15.14. Provider adapter layer
Makes the system portable across providers, models, and runtimes.

### 15.15. MCP and API integration layer
Exposes the system as an external context service.

## 17. Structure of a bounded context bundle

A canonical bundle should include:

1. **Purpose** — why this bundle exists
2. **Target mode** — what kind of task/model step it supports
3. **User frame** — stable profile and durable preferences
4. **Relevant facts**
5. **Active state**
6. **Open loops**
7. **Constraints**
8. **Recent decisions**
9. **Risk or uncertainty notes**
10. **Optional artifact references**
11. **Optional tool hints**
12. **Bundle metadata** — scope, freshness, confidence, generated_at, expiry

The bundle must be compact, structured, and task-shaped.
It must not be a dump of all available memory.

## 18. Decisions the context layer must own

The context layer must decide:
- relevancy;
- scope eligibility;
- priority;
- boundedness;
- freshness;
- confidence thresholds;
- conflict handling;
- deduplication;
- memory vs state classification;
- handoff packaging;
- summary refresh triggers;
- archival triggers;
- retention behavior;
- policy restrictions;
- model/provider-specific packaging constraints.

---

## 19. Decisions the context layer must not absorb

To prevent uncontrolled system sprawl, the context layer must not:
- replace the main model as task executor;
- become the full application business logic;
- collapse into a generic retrieval subsystem;
- become only a UI concern;
- assume exclusive ownership of non-context product logic;
- force a single provider lock-in.

---

## 20. Preferred architectural stance

The strongest current architecture is hybrid, not pure-LM-first.

Recommended composition:
- rules for hard gating;
- typed policies;
- ranking and scoring logic;
- optional lightweight semantic models for classification;
- layered storage;
- tool-mediated model access;
- bounded bundle packing;
- external write gate;
- explicit audit trail.

This gives more control and stability than relying on one LLM to govern all context decisions.

## 22. MCP and external integration role

The system should be usable as an external context infrastructure service.

### It should be connectable to
- Codex through MCP;
- ChatGPT through MCP-compatible tools/resources/prompts surfaces where supported;
- other agent runtimes through tool or API integration;
- local or cloud orchestration environments.

### MCP role in this architecture
MCP is not the whole system.
It is the standard interface surface that allows the system to expose:
- context tools;
- bounded resource views;
- prompt-support artifacts;
- governed access patterns.

The context intelligence itself remains inside the orchestrator.

## 23. Canonical example flow

### Scenario
A user returns to an earlier topic and wants to continue from the prior state.

### What the system does
1. Detects continuation intent.
2. Resolves relevant scopes.
3. Retrieves project memory and active state.
4. Builds a bounded bundle.
5. Sends that bundle to the main model.
6. Allows the model to request expansion if needed.
7. Receives the final answer.
8. Extracts memory and state candidates.
9. Lets the write gate decide what becomes canonical.
10. Updates continuity artifacts for the next interaction.

---

## 24. Signs of a successful system

The system is successful if:
- new sessions do not restart from zero;
- the model receives sufficient but not bloated context;
- active state survives reliably;
- memory remains structured rather than noisy;
- handoff between sessions and agents works;
- the system can justify why a bundle was produced;
- provider switching does not destroy continuity;
- context access remains governed and explainable.

---

## 25. Main risks

1. Reducing the system to RAG.
2. Reducing the system to vector search.
3. Letting the model write canonical memory directly.
4. Mixing memory and state.
5. Failing to enforce bounded packing.
6. Making the architecture provider-agnostic only in name.
7. Missing audit and evaluation.
8. Allowing scope and policy logic to remain implicit.
9. Treating summaries as the only truth.
10. Over-embedding runtime-specific assumptions into the core design.

---

> Personal Context Orchestrator is a provider-agnostic control layer that stores, selects, packs, governs, and transfers bounded context for models and agents across sessions, tasks, workflows, providers, and execution environments.

We are not designing a memory feature for chat.
We are not designing a simple retrieval engine.
